# 架构

Clash Halo 是一个“界面可完全退出、代理继续运行”的桌面代理客户端。本文记录
实现中的实际结构；README 记录如何构建与验证。

## 1. 进程模型（Windows）

```text
Flutter UI 进程（普通权限）
  │  FFI: CreateFileW / PeekNamedPipe / ReadFile / WriteFile
  │  受限命名管道（仅当前用户可访问）
  ▼
halo-host.exe（托盘后台，普通权限）
  ├─ 业务配置：SQLite（nodes / subscriptions / settings）
  ├─ 运行状态：内存快照，唯一的运行时事实来源
  ├─ 系统代理：写注册表，记录原值与应用写入值
  ├─ sing-box.exe（普通代理模式，独立进程，官方构建）
  └─ halo-tun-service.exe（TUN 服务，首次启用 TUN 时安装一次，LocalSystem）
       └─ sing-box.exe（TUN 入站，服务持有作业对象，宿主退出即停止）
```

TUN 只有服务后端：构建不产出 `halo-tun-helper.exe`，缺失服务二进制时宿主在启用前
直接报 `tun_unavailable`，不会退回到第二条提权路径。核心进程统一由
`internal/tunsup.Runner` 启动、持有和停止（作业对象、CTRL_BREAK、日志轮转只有一份
实现）。

关键约束：

- UI 进程退出不停止代理；托盘可随时重新拉起 UI。
- **普通代理模式与 TUN 互斥**：同一时刻上面几个 `sing-box.exe` 分支只有一个在跑，
  因为它们都要绑定本机 mixed 入站的同一个端口（默认 7890）。开启 TUN 会停掉普通
  内核，开启系统代理会停掉 TUN 内核。这由宿主强制，不是 UI 的约定：
  - `tunEnable` 成功之后调用 `tunTakesOverSystemProxy()`，关闭系统代理；
  - `SetSystemProxy(true)` 先调用 `leaveTunForProxyMode()`，停掉 TUN 再写注册表；
  - `coreStart` 在 TUN 已启用时直接拒绝；`restoreNormalCore` 在 TUN 接管端口时
    不启动普通内核（`tunnelOccupiesInboundLocked`）。

  曾经缺少后两条，结果是 TUN 起来之后普通内核被「恢复」并与它争用 7890，子进程以
  `bind: Only one usage of each socket address` 秒退——用户看到的是「代理内核崩溃」，
  而 TUN 其实工作正常。界面与托盘必须如实呈现这个二选一（见
  [设计规范](设计规范.md) 的对应条目）。

  两个开关都可以开启，成功的那个生效、另一个被自动关闭——不是把哪一个置灰。用户
  从 TUN 回到普通代理的入口就是那个开关本身。
- **运行状态**只有 `halo-host.exe` 能读写，UI 通过管道请求。
- **业务数据**（SQLite 里的节点、订阅、设置）由 Dart 进程直接读写：宿主的 Go 代码
  不链接 SQLite（`native/windows` 下没有 sqlite 依赖），`AppController._openStore()`
  用 `packages/storage` 打开 `clash-halo.db` 并写入，宿主只拿到 UI 通过
  `tray.publish` 投影过去的节点代号与名称。

  这条曾经写成"只有宿主能读写数据库"，与代码不符，代价是有人（包括代理）会以为
  改库必须经过管道。多进程并发是安全的：WAL 模式允许一个写者与多个读者，
  `busy_timeout` 为 5s，写事务都是 `SAVEPOINT` 包起来的短事务。`apps/cli` 正是利用
  这一点在不开界面的情况下导入订阅。
- 管道名字由数据目录派生，因此不同安装互不干扰（见 §3）。

### 1.1 内核的"状态"与"意图"是两件事

快照里有两个容易混淆的字段，分开它们是为了修一个真实缺陷：

| 字段 | 含义 | 重启后 |
| --- | --- | --- |
| `coreState` | 现在有没有活着的内核进程 | **强制重置为 `stopped`**（死进程不能报成活） |
| `coreWanted` | 用户是否**希望**内核在跑 | 原样保留 |

早期只有 `coreState`。宿主重启时它被重置，而没有任何东西记录"用户本来要它跑"，
于是每次启动内核都是关的，用户得为一个已经应用过的节点再按一次「启动」。
现在 `coreWanted` 承担意图：`core.start`、`config.apply(startCore=true)` 置 true，
`core.stop` 置 false，宿主启动后由 `App.ResumeCore` 按它恢复。

恢复的边界（都是有意的）：

- **不恢复系统代理**。写注册表是有副作用的动作，崩溃后可能留下半改状态，不该在
  启动时无声地再写一遍。内核回来，接管流量仍然是显式动作。
- **不恢复 TUN**：需要管理员授权，启动时无人可答。
- **不违背用户**：主动 `core.stop` 会清掉意图，下次启动不会复活。
- 旧快照没有该字段时，用"上次是否在运行"推断意图（见 `state.load`），
  避免升级把已有用户的功能悄悄关掉。

## 2. 单一事实来源

| 数据 | 权威方 | 原因 |
| --- | --- | --- |
| 内核状态、当前节点、系统代理、TUN、日志 | host 内存快照 | UI 可能不在运行 |
| 测速结果、流量采样 | host 内存会话 | 跟宿主进程同生命周期；界面退出不丢失，托盘退出或宿主退出清空 |
| 节点列表、订阅、偏好设置 | SQLite | 用户编辑的持久业务数据 |

`session.get` 返回测速批次与结果，`traffic.get` 返回流量累计、峰值、40 点历史与
活动连接数。界面退出只关闭自己的 `:vpn`/UI 进程，宿主继续测量；界面重新连接时
用这两个动作覆盖本地视图，不在本地重新累计，因此关闭期间的数据不会归零。

两者只在读取时合并，避免旧快照覆盖用户刚导入的节点。管道断线重连后，host
返回**全新快照**而不是增量补齐，因此不会出现版本错位。

## 3. 通信契约

单行 JSON（NDJSON），三种帧：

```jsonc
// 请求
{"v":1,"id":"7","action":"snapshot.get","params":{}}
// 响应
{"v":1,"id":"7","ok":true,"result":{...},"stateVersion":3}
// 事件
{"v":1,"event":"state.changed","seq":12,"data":{...}}
```

- `v` 不是当前协议版本时返回 `version_mismatch`，不尝试兼容。
- 错误码是有限集合，Dart 与 Go 使用同一套字符串（见 `docs/验证记录.md` 的
  一致性检查），避免 UI 只能靠猜。
- 事件带单调递增 `seq`，客户端可据此丢弃乱序帧。

管道名：`\\.\pipe\clash-halo-host-v1-<hash>`，其中 hash 为数据目录规范化
（小写、反斜杠转斜杠、去空段）后 UTF-8 字节的 FNV-1a 64 位值。Dart 与 Go
各自独立实现，并有跨语言向量测试保证两侧一致（`packages/contracts/test/
pipe_name_test.dart` 与 `native/windows/internal/contract`）。

## 4. 配置应用流水线

```text
候选配置 → 哈希校验 → 能力校验 → 内核 validate → 保存可恢复的上一版本
        → 应用 → 健康检查 → 失败则回滚
```

失败回滚是这条链路存在的主要理由：写坏配置不能让用户既没有旧配置也没有新
配置。健康检查通过后才把 `configVersion` 递增。

## 5. 权限边界

| 能力 | 需要提权 | 实现状态 |
| --- | --- | --- |
| 系统代理（注册表） | 否 | 已实现，停止时仅在值仍等于我们写入的结果才恢复 |
| TUN 设备创建 | 是 | 服务：首次启用 TUN 时安装一次，之后无需提权；闭集命令 + 配置内容校验 |
| Android VPN | 系统授权 | 已实现：独立 `:vpn` 进程运行 libbox，VpnService 建 TUN；状态经 `vpn-state.json`，启停经显式 Intent。真机流量已验证，后台存活/网络切换待测（见 `native/android/README.md`） |

TUN 采用**首次启用时安装一次的本地服务**，安装包不注册服务。首次
`tun.setEnabled {enabled:true}` 会弹出一次 UAC，安装 `halo-tun-service.exe`
并启动它；此后启用/关闭 TUN 都通过命名管道请求服务，不再提权。服务以
LocalSystem 常驻、空闲时不运行内核；宿主退出或断管后服务停止内核并清理路由/
适配器；服务重启不恢复内核。源码与测试见 `native/windows/internal/tunservice`，
设计与取舍见 [`docs/tun-service-design.md`](tun-service-design.md)。

服务只执行受保护目录中、摘要与构建时固定值一致的内核；配置由宿主生成，服务
读取、校验并复制到自己的受保护目录后才启动，运行期间用户改不了它。控制管道
的 DACL 只允许安装者 SID、SYSTEM 与管理员。管理员进程不接受任意命令、任意
可执行路径或任意文件写入（`tunservice` 的闭集校验与配置内容校验有单测覆盖）。

服务是唯一的 TUN 后端。没有服务二进制的布局（构建不完整或旧安装）在启用前就
报告 `tun_unavailable`，不会退回到每次启用弹一次 UAC 的助手路径。

TUN inbound 同时声明 IPv4 `172.19.0.1/30` 与 IPv6 `fdfe:dcba:9876::1/126`。
Windows 的 `strict_route` 在 TUN 没有 IPv6 地址时会用 WFP 阻断 IPv6，
`::1` 也随之不可达；本地 `localhost` 开发服务器会因此连接失败。

设置里的 IPv6 开关默认关闭：关闭时 DNS 对 AAAA 返回无记录的成功响应，应用只使用 IPv4，避免把
IPv6 连接交给没有 IPv6 出口的节点；只有节点和网络都具备 IPv6 能力时才开启。

TUN 是三层入口，连接建立时只有目的 IP。域名由 TLS SNI、HTTP Host 或 QUIC SNI
携带，生成器因此在 `route.rules` 首位放一条 `sniff`（`tls`/`http`/`quic`，300ms）。
连接页的「主机」列和 `geosite-*` 域名规则都依赖它；缺少该规则时，TUN 连接只能
按 IP 匹配并显示为纯 IP。

TUN 启用和宿主启动时还会核对 Windows 注册表的实际代理状态：快照说系统代理已关闭，
但 `ProxyEnable=1` 仍指向本应用的 `127.0.0.1:7890` 时，会清理这个残留值，否则浏览器
会继续走代理而不是 TUN。

## 6. 有界日志

- 按大小与数量双限滚动，超出即丢弃最旧文件。
- 不记录凭据：订阅 URL 的输出经过脱敏（`displayUrl`）。
- 日志大小计入快照（`logBytes`），UI 可显示而无需读取文件。

## 7. 订阅刷新

仅在 UI 连接期间刷新（host 跟踪 UI 客户端数）。UI 关闭后不产生网络请求，
避免后台无意义流量与凭据长期驻留内存。

## 8. 模块边界

```text
apps/flutter          界面与交互，唯一依赖 Flutter
packages/contracts    协议模型、错误码、版本常量（纯 Dart，无 IO）
packages/domain       节点/订阅模型、导入、批量操作、指纹（纯 Dart）
packages/config       sing-box 配置生成与能力清单（纯 Dart）
packages/storage      SQLite schema、仓储、备份（唯一依赖 sqlite3；Windows 用系统 winsqlite3.dll）
native/windows        Go 宿主的装配与 IPC 分发（composition root）
  internal/connapi       Clash API 查询/关闭、回环校验、端点缓存
  internal/configstore   配置文件、候选/提升/回退、当前哈希与版本
  internal/apply         配置应用管线（校验→提升→启动→健康检查→回退）
  internal/corelife      普通内核的启动/停止/恢复状态机
  internal/tunadmin      TUN 服务的安装/状态/卸载
  internal/tunsup        TUN 核心运行器、作业对象、状态类型与进程/适配器判定
  internal/tunservice    LocalSystem 服务控制器、命名管道与配置闭集校验
native/android        Kotlin VPN 模块（:vpn + libbox）：真机流量、通知/状态、本地测速已验证；后台存活/网络切换待测
```

`App` 只保留 Dispatch、跨域锁顺序与 TUN enable/disable 编排；各域不反向依赖
`app`。`domain`、`config`、`contracts` 不依赖 `dart:io` 之外的能力，因此可以在
无平台的单元测试中完整覆盖；`storage` 与 `native` 才承担真实副作用。
