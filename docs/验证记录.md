### 1.1 live 测试覆盖了什么

`apps/flutter/test/host_live_test.dart` 启动真实的 `halo-host.exe`，通过
生产用的 FFI 传输连接真实命名管道，并让 host 拉起真实 `sing-box.exe`：

1. `snapshot.get` 返回真实运行状态；
2. `host.status` 报告解析到的内核路径；
3. 应用有效配置后内核进入 running，`configVersion` 递增；
4. 无效配置被拒绝（`config_invalid`），已在运行的内核不受影响；
5. 应用有效配置后内核进入 running，`configVersion` 递增；
6. 无效配置被拒绝（`config_invalid`），已在运行的内核不受影响；
7. `tunSupported` 与内核目录下是否真实存在 `halo-tun-service.exe` 一致；两者都在时
   断言状态为 `disabled`（此时不调用启用，避免在自动运行中弹出 UAC）；缺少服务
   程序时启用返回 `tun_unavailable` 且绝不报告已启用；
8. `log.tail` 返回真实日志行；
9. `host.shutdown` 让进程与管道一起关闭。

第 3、4 项无法用假管道证明：它们依赖真实的进程启动、健康检查与回滚。

## 2. 跨语言一致性

管道名由数据目录派生，两侧必须给出相同结果，否则 UI 连不上 host。两侧各自
独立实现 FNV-1a，并用固定向量对齐：

| 输入 | 期望后缀 | Dart 测试 | Go 测试 |
| --- | --- | --- | --- |
| `D:/project/clash-halo` | `3f9aa21224b50de8` | 通过 | 通过 |
| `a` | `af63dc4c8601ec8c` | 通过 | 通过 |

错误码同样对齐：Go 的 `contract.Err*` 常量使用与 Dart `HaloErrorCode` 完全
相同的字符串（如 `version_mismatch`、`unsupported_capability`、
`task_canceled`、`already_running`、`elevation_required`）。这是一次实际
修复——早期两侧各自命名，UI 无法可靠判断错误类型。

该一致性现在由 `packages/contracts/test/error_code_parity_test.dart` 强制：
它解析 Go 常量块，只要 host 能返回某个码而 Dart 没有对应描述就失败。补测时
发现 `elevation_required` 确实缺失（host 会返回、UI 只能拿到原始字符串），
已补上。

### 3.1 TUN 真实提权运行（2026-11-03 实测）

真实提权需要人工在桌面点击 UAC，因此这条用例默认跳过，只在显式指定时运行：

```bash
cd native/windows
HALO_TUN_E2E=1 HALO_SINGBOX=<sing-box.exe> \
  go test ./e2e/ -run TunEndToEnd -v -count=1 -timeout 10m
```

实测输出要点（原样摘录）：

```text
tun.setEnabled result: map[tunAdapter:clash-halo-e2e tunElevated:true
                          tunMessage:TUN 已启用 tunPid:18616 tunState:enabled]
adapter status: "Up|sing-tun Tunnel"
adapter IPv4 addresses: "172.19.0.1"
default route: singbox_tun metric=0; WLAN metric=0; clash-halo-e2e metric=0
request sourced from 172.19.0.1: status=200 bodyBytes=577
adapter bytes after: rx=27316 tx=17780 (delta rx=11528 tx=6718)
tun.setEnabled(false) result: map[tunAdapter: tunElevated:false tunPid:0 tunState:disabled]
adapter removed after disable
```

这条记录证明的是：真实 UAC 授权成功、wintun 适配器被真正创建（网卡描述
`sing-tun Tunnel`，状态 `Up`）、`/30` 地址下发、`auto_route` 安装默认路由、
**流量确实经过隧道**、以及关闭后适配器消失且提权内核进程退出。

为什么请求要把源地址绑定到 `172.19.0.1`：本机已存在另一个 TUN 适配器
（`singbox_tun`），它同样注册了 metric 0 的默认路由。此时“请求成功”不足以
证明流量走了我们的隧道，而绑定只属于该适配器的源地址可以强制数据包进入它。
适配器计数随之增长，才是流量确实被承载的证据。

未在真实提权下验证的相邻部分：

- `strict_route`：默认开启时内核会安装防火墙规则，其回滚依赖内核正常退出；
  本次验证刻意使用 `strictRoute:false`，因此该路径未验证。
- 干净机器上的 wintun 驱动首次安装：本机 `wintun` 内核驱动（`wintun.sys` 与
  运行中的 `wintun` 服务）在本次验证**之前**就已存在，因此没有验证过
  由本应用在有史以来未安装过该驱动的机器上完成首次驱动安装。

边界的证据；该二进制已在 2026-11-07 删除，不再随任何构建产出。）

## 3.2 界面启动失败时的排查

界面打不开（窗口一片灰、什么文字都没有）属于**最难反馈**的一类故障：release
下 Flutter 的兜底就是一个无文字的灰块，而窗口只在首帧渲染成功后才会 `Show()`，
所以“界面没出现”和“界面崩了”在用户眼里是同一种现象。现在有三条通道：

1. **窗口内**：任何 build 期异常都由 `haloErrorWidget` 显示异常文本、来源与日志
   路径，不再是一个空灰块。
2. **日志**：`FlutterError.onError` 与 `PlatformDispatcher.onError` 把异常与完整
   堆栈追加到 `<数据目录>/logs/ui-error.log`；数据目录不可写时回退到系统临时
   目录。相同的重复异常只记一次。
3. **控制台**：从终端启动可以直接看到 Dart 的未捕获异常（这也是本次定位到
   `Bad state: 数据库不可用` 的方式）：

```bash
# 直接运行并捕获 Dart 侧输出
./clash-halo.exe > ui.out 2> ui.err
```

数据库打不开时，界面会显示整页说明（数据目录 + 异常原文 + 排查建议），而不是
让每个页面在 `build` 里各崩一次：

![数据库失败时的界面](images/ui-store-unavailable.png)

*(图：本地截图产物，未入库；需要时用 `scripts/capture-window.ps1` 现生成。)*

截图验证注意：本机为 200% 缩放（2560×1600 屏幕，窗口 1180×760 逻辑 =
2360×1520 物理）。**DPI-unaware 的截图进程只看得到窗口的左上四分之一**，
会被误判成“布局溢出/文字被截断”。截图前必须调用
`SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`。

## 3.3 导入 V2Ray 配置的端到端验证

`apps/flutter/test/v2ray_import_live_test.dart`(标签 `live`)不 mock 任何一环:

```text
vmess:// 分享链接 → 真实导入器 → 真实生成器 → 真实 halo-host.exe
   → 真实 sing-box → 真实 HTTP 请求取回内容
```

**怎么证明流量真的走了 VMess。** 客户端请求 `http://203.0.113.9:8080/`
(TEST-NET-3,永不可路由),而本地 VMess 服务端用 route 动作把所有目的地址改写到
回环上的测试站点。于是:

- 直连或不走代理的请求必然失败——那个地址不存在;
- 只有服务端的改写才够得着测试站点;
- 因此拿到 200 与站点令牌,就证明请求确实经过了
  `客户端 → mixed 入站 → vmess 出站 → vmess 入站 → 站点`。

同时断言本地服务端日志出现入站连接,证明 VMess 握手真的完成了,而不只是"能连通"。
用本地服务端替代远程 V2Ray 服务器,是为了让测试不需要任何真实凭据与外网。

实测结果(2026-11-03):**通过**。

```bash
cd apps/flutter && \
  HALO_HOST_EXE=<halo-host.exe> \
  HALO_CORE_EXE=<sing-box.exe> \
  ../../.tools/flutter/bin/cache/dart-sdk/bin/dart.exe test test/v2ray_import_live_test.dart
```

这个测试第一次运行就抓到一个阻断性缺陷,见 §4 最后一行。

## 4. 修复的真实缺陷（验证过程中发现）

| 缺陷 | 影响 | 修复 |
| --- | --- | --- |
| 管道名全局固定 | 测试与真实安装互相抢占 | 改为按数据目录派生 |
| Go 与 Dart 错误码命名不一致 | UI 无法可靠区分错误 | 统一为 Dart 词表 |
| live 测试把数据目录建在 `%TEMP%` | 沙箱子进程创建锁文件被拒绝，测试全红 | 改到工作区内 |
| live 测试固定端口 27890 | 上个用例残留内核占端口，误报“配置被拒” | 每次分配空闲端口，teardown 清理子进程 |
| `share_link` 的 `sourceFormat` 与枚举不一致 | 导入来源显示错位 | 统一为 `share_links` |
| Dart 无法用 `dart:io` 连接 Windows 命名管道 | UI 完全无法通信 | 改用 FFI 调用 Win32 |
| 逐块解码 UTF-8 | 中文日志乱码 | 缓存原始字节，按行解码 |
| **`SHELLEXECUTEINFOW.fMask` 误声明为 `uintptr`** | 结构体 120 字节而非 112，`hwnd` 之后每个字段偏移 4 字节，shell 从错误的槽位读取 verb/文件名/参数，只表现为误导性的 `Access is denied`，提权完全不可用 | 按 SDK 头文件改为 `ULONG`（4 字节），并用 `unsafe.Offsetof` 断言全部 15 个字段偏移与 `sizeof==112`（`internal/elevate`） |
| `SafeJoin` 用进程工作目录解析相对路径 | 合法的 `log.output: "core.log"` 被当成越界而拒绝，TUN 无法用相对日志路径 | 新增 `ResolveUnderRoot`，相对路径按数据目录解析（与内核实际工作目录一致），并补相对路径穿越 `..\..\` 的拒绝用例 |
| 未提权拒绝返回退出码 2 | 与文档化的 3 不符，宿主的 `hintForExitCode` 永远不生效，用户看不到“缺少管理员权限”的提示 | 提权检查单独返回 `exitNotElevated`（3），实测已确认 |
| `tun_unavailable` / `elevation_required` 的中文描述仍写“本版本尚未验证” | TUN 实现后这些文案会让用户以为功能不存在 | 更新为“需要管理员授权/提权被拒绝”，并让 parity 测试断言文案不再包含“未验证” |
| 旧的 TUN 测试断言 `elevation_required` + `unverified` | 行为已改变，测试会给出假绿/假红 | 改写为断言“无助手时 `tun_unavailable`”，并新增以安全缝替代提权的 TUN 状态机测试 |
| sing-box 1.12 起删除了 `inet4_address`/`inet6_address` | 按旧文档生成的 TUN 配置会被内核直接拒绝（`legacy tun address fields … removed in 1.12.0`） | 改用 `address` 数组字段，并以共享 fixture + 真实 `check` 双端固定 |
| **数据库打不开时整个界面变成一块灰色空窗** | `main.dart` 的 `initState` 用会抛异常的 `settingsRepo` 读主题偏好，数据库不可用时异常从**首次 build 中逃逸**，一帧都没有渲染成功。release 下 Flutter 的兜底是**一个没有任何文字的灰色方块**，窗口又只在首帧后才 `Show()`，用户只看到“灰色底、啥也没有”，且日志里一个字都没有，无法反馈 | 1) 新增不抛异常的 `storedSetting`；2) `ErrorWidget.builder` 换成可读的 `haloErrorWidget`（显示异常文本、来源、日志路径）；3) `FlutterError.onError` / `PlatformDispatcher.onError` 写入 `logs/ui-error.log`；4) 数据库失败时用整页说明替代各页面，避免每个页面在 `build` 里各崩一次 |
| 数据库失败只有一行底部提示条 | 原因（含数据目录、异常原文）看不到，用户不知道是权限、磁盘还是文件锁 | 改为整页说明：标题、数据目录、完整异常、两条排查建议；删除重复的 `_StoreErrorBar` |
| **深色模式下大量文字/图标失读** | 关闭态、状态点一律用 `lightTextSecondary`，语义色只有浅色一套：`#C42B1C` 红与 `#107C10` 绿画在 `#2A2A2A` 卡片上对比度不足，等于看不见 | 颜色拆成中性/强调/语义三层，语义色各有明暗两值；新增 `HaloPalette.of(context)` 与 `HaloColors.adapt`，`StatusChip`/`InfoRow` 内部自动换色；清理 6 处写死语义色的 `Text`/`Icon` |
| 深色界面配白色标题栏 | 用户选「深色」而系统是浅色时，runner 只读系统主题，标题栏仍是白色 | 新增 `clash_halo/theme` 方法通道，Dart 在主题变化与 `didChangePlatformBrightness` 时下发 `setDark`，由 `DwmSetWindowAttribute` 设置 |
| 键值行在宽窗口下留出约 200px 空洞 | `InfoRow` 用 flex 3/5，短标签与值被推到卡片两侧 | 标签列固定 132px，值紧随其后 |
| 「分流与 DNS」页在 800×600 下纵向溢出 46px | 左栏是固定 380 宽的 `Column`，字号上调后放不下，底部卡片被裁掉 | 左栏改为可滚动 `ListView`，卡片同时铺满栏宽 |
| 卡片内 `ListTile` 触发墨水断言 | `SectionCard` 用带底色的 `DecoratedBox` 包内容，遮住最近 `Material` | 阴影留在外层，表面改用 `Material`，`ListTile` 重新有墨水效果 |
| **生成的配置内核根本起不来（所有模式）** | 本地 DNS 服务器的 `detour` 指向空 `direct` 出站。该检查在 **DNS 传输启动时**执行，`sing-box check` 不覆盖，所以配置"校验通过"、内核启动即 FATAL：`start dns-transport: start dns/udp[local]: detour to an empty direct outbound makes no sense`。用户点"启动"永远失败，界面只能报"健康检查未通过" | 本地 DNS 不再带 `detour`；改为在 route 规则里按 `dns.directServer` 的 IP 加一条 `ip_cidr → direct`，保持"本地解析走直连"的原意（否则代理会拿代理自己的服务器域名去解析）。新增"每种模式都真正启动内核"的测试——只跑 `check` 抓不到这类缺陷 |
| **托盘模式宿主关闭后残留，界面进程持续增殖** | 三处缺陷叠成一条正反馈：① `shutdown()` 走完所有收尾后，托盘模式仍停在 `systray.Run` 的消息循环里，进程不退出——`host.shutdown` 回了 `quitting`、管道也关了，但 `host.lock` 还被这个僵尸进程握着；② 下一个界面探测 `--status` 得到 `running:false`（管道没了），于是启动"新"宿主；③ 该宿主抢锁失败，`launchUI()` 又开一个窗口，新窗口再启动宿主……实测每约 2 秒多一个 `clash-halo.exe`，25 秒内从 3 个涨到 15 个。界面自身也从未有单实例，双击几次就是几个窗口 | ① `shutdown()` 里 `systray.Quit()` 离开消息循环，并加 `exitAfterShutdown`：收尾完成后**进程必须结束**，超时也强制 `os.Exit`；② 宿主新增 `--from-ui`，由界面拉起的宿主抢锁失败时**不再开窗口**（`shouldOpenUIOnHandOff`），用户手动启动仍照常打开；③ Windows runner 新增 `single_instance.cpp`：按数据目录建 `Local\` 互斥体，第二个实例只把已有窗口置前（`SetForegroundWindow`，失败则闪烁任务栏）然后退出，并修正 `host.shutdown` 的时序——先回响应再由 IPC 服务 `AfterReply` 触发退出，避免响应被关管道吃掉 |

### 内核不随宿主恢复（已修复）

现象：应用节点后关闭再打开应用，内核不启动，必须手动点一次「启动内核」。

原因：快照的 `coreState` 在每次宿主启动时被**刻意**重置为 `stopped`（不能让死进程
看起来还活着），但没有任何字段记录"用户本来希望它运行"，所以重置之后无处可恢复。
`方案.md` 的"默认关闭、不自动连接"被实现成了"连内核也不恢复"，把两件事一起砍掉了。

修复：新增 `coreWanted`（意图，跨重启保留），`App.ResumeCore` 在宿主启动、管道就绪后
按它恢复内核。**不恢复系统代理**、不恢复 TUN、主动停止会清掉意图。

实测（`.tmp/resume-e2e` / `.tmp/resume-stop`，真实内核）：

```text
session1: config.apply → core started pid=21220
          systemProxy.set enabled=true → 托盘 active
          host.shutdown → core pids: 0
session2: 重新启动宿主 → [host] 已恢复上次的内核 pid=6728 config=active.json（系统代理保持原样）
          snapshot: coreState=running corePid=6728 coreWanted=true

反向用例: core.stop → coreWanted=false → 重启后 coreState=stopped, core pids: 0
```
