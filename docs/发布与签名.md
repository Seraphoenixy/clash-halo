# Windows 发布与签名

日期：2026-11-03。本文记录本项目在 Windows 上遇到的启动提示、实测结论，以及发布签名流程。

所有 `.ps1` 一律用 **pwsh（PowerShell 7+）** 运行，脚本头部有 `#Requires -Version 7.0`：
Windows PowerShell 5.1 会用本地 ANSI 代码页解码无 BOM 的脚本，中文与破折号会直接变成语法错误。

## 1. 启动提示分三种，成因不同

| 提示 | 触发条件 | 消除方式 |
| --- | --- | --- |
| SmartScreen「Windows 已保护你的电脑」 | 文件带「来自 Internet」标记（Mark-of-the-Web）**且**系统开启了「检查应用和文件」 | 去掉标记（`Unblock-File`）；对外发布则需公网可信签名 |
| 用户账户控制「是否允许此应用对你的设备进行更改？」 | 进程请求提权：首次启用 TUN 时 `halo-tun-service.exe --install` 一次，卸载服务时一次 | 签名后发布者不再是「未知发布者」 |
| 杀毒/安全软件拦截 | 各家策略 | 签名可去掉「未签名」信号，但不保证 |

`Clash Halo` 的正常布局里只有 `halo-tun-service.exe`（首次启用 TUN 的安装/卸载）
会请求管理员权限，**主界面与后台都不提权**；
`clash-halo.exe` 的内嵌清单是 `asInvoker`，`halo-host.exe` 与 `halo-tun-service.exe`
目前没有为准入而嵌入清单（见 §5）。

## 2. 签名流程

```powershell
# 查看现状（只读，不改任何文件）
pwsh -File scripts/sign-windows.ps1 -Report

# 发布：用公网可信证书签名（PFX 或本机证书库里已有的证书）
pwsh -File scripts/sign-windows.ps1 -PfxPath .\codesign.pfx -PfxPassword '***'
pwsh -File scripts/sign-windows.ps1 -Thumbprint <SHA1>

# 本机开发：自签名并让当前用户信任它
pwsh -File scripts/sign-windows.ps1 -SelfSigned -TrustSelfSigned

# 一并去掉「下载」标记（从 zip 解压出来的副本会带）
pwsh -File scripts/sign-windows.ps1 -Unblock
```

签名对象是 `clash-halo.exe`、`halo-host.exe`、`halo-tun-service.exe`、
`sing-box.exe`。
算法 SHA-256，默认带 RFC3161 时间戳；时间戳服务器不可达时脚本会去掉时间戳重签并说明。

安装包本身也要签名：`-FilePath` 只签指定的那一个文件，跳过上面那个固定清单。

```powershell
pwsh -File scripts/sign-windows.ps1 -FilePath build\release\clash-halo-0.1.0-setup.exe -SelfSigned
```

`scripts/build-installer.ps1` 也接受同一组签名参数，打完包直接签：

```powershell
pwsh -File scripts/build-installer.ps1 -SelfSigned -TrustSelfSigned
```

注意签名会改变文件内容，所以**先打包，后签名**；对安装包签名之后 SHA-256 会变，
构建脚本在签完会重新计算再打印。

构建脚本可以直接带签名：

```powershell
pwsh -File scripts/build-windows.ps1 -SelfSigned -TrustSelfSigned
```

**每次重新构建后必须重新签名**：签名会改变文件，重建则签名消失，提示可能随之回来。

## 3. 本次实测结论（2026-11-03）

在本机（Windows 10 企业版 19045）实测：

- 四个二进制原本 `NotSigned`，`clash-halo.exe` 经 shell 启动会被拦下，
  返回「操作已被用户取消」（用户在提示上选择了拒绝）。
- 本机没有任何 `clash-halo.exe` 带 Mark-of-the-Web（`dir /r` 与 `Get-Item -Stream` 双查），
  也没有 AppLocker、WDAC、智能应用控制（SAC）或 Defender ASR 规则。
- 用自签名证书签名，并把证书导入**当前用户**的 `Root` 与 `TrustedPublisher` 之后，
  四个文件状态变为 `Valid`，发布者为 `CN=Clash Halo, O=Clash Halo Project`。
- **但签名没有消除这个提示。** 用户在资源管理器里双击 `clash-halo.exe` 时，
  弹出的提示说明 **SmartScreen 无法联网检查**。
- 把诊断期间改过的用户级开关
  `HKCU\...\AppHost\EnableWebContentEvaluation` 恢复为原始未设置状态后行为不变。

### 3.1 这个提示的真实成因：信誉检查拿不到云端裁决

用户提供的截图把提示定性了：它是 Windows 的 **「打开文件 - 安全警告」**
（标题「打开文件 - 安全警告」，问题「你想运行此文件吗？」，按钮「运行(R) / 取消」），
**不是**签名失败——同一张截图里「发行商」已经显示 **Clash Halo**，
说明 Authenticode 签名与受信任发布者都已生效。

本机 `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\AppHost\EnableWebContentEvaluation = 1`，
即「应用和文件检查」是开启的；而这台机器的出网走本地代理
（`D:\project\Nornia\Directory.Build.props` 里也记录了“本地代理无法完成 NuGet 的 TLS 请求”），
信誉检查连不上自己的服务，于是对每次启动都只能弹这个框。

用一个排除了“文件被标记”的诊断可以确认它不是 Mark-of-the-Web：
`dir /r`、`Get-Item -Stream *`、`FindFirstStreamW` 三种方式都显示这些 exe
只有一个 `::$DATA` 流，没有任何 `Zone.Identifier`；
也没有 AppLocker、WDAC、智能应用控制（SAC）或 Defender ASR 规则。

两个后果要记住：

1. **签名离线时救不了它**：检查要的是云端裁决，不是本地证书链；
   自签名只是把签名状态变成 `Valid`、把「发行商」填上。
2. **「取消」不会被记住，「运行」才会**：在这个框上点「运行(R)」后，
   Windows 会为该文件（按内容）记住决定，同一份构建不再提示；
   点「取消」等于没发生过，下次双击照旧弹。
   每次重新构建 exe 内容都会变，所以“记住”也会失效。
   这一条解释了为什么“每次都弹”：一直点取消，自然每次都问。

### 3.2 可选的修法

| 目标 | 做法 |
| --- | --- |
| 只让本机安静下来（保留系统其余保护） | 在提示上点「仍要运行」一次；或按 §3.3 关闭「应用和文件检查」 |
| 本机长期不再提示 | §3.3 的关闭命令（需要管理员），或修好出网让 SmartScreen 能拿到裁决 |
| 对外分发不提示 | 公网可信的代码签名证书（OV/EV、开源签名服务、云签名），见 §2 |

### 3.3 关闭「应用和文件检查」（需要管理员）
图形界面：Windows 安全中心 → 应用和浏览器控制 → 基于声誉的保护 →
关闭「检查应用和文件」。

或在**管理员** pwsh 里执行：

```powershell
Set-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\AppHost' `
  -Name EnableWebContentEvaluation -Value 0 -Type DWord
```

注意这是降低防护的开关，属于本机取舍；对外分发仍应签名。
本仓库的常规用户权限下改不动 `HKLM`（会得到“拒绝访问”），所以这一步必须由
管理员执行。

## 4. 低完整性启动：本机没有托盘图标的真正原因（结论：按路径判定）

2026-11-03 实测。**触发条件是启动路径，不是签名、不是清单、不是语言。**

| 被测对象 | 位置 | 完整性级别 | 托盘图标 |
| --- | --- | --- | --- |
| `Lumen.App.exe`（未签名 C#） | `D:\software\Lumen-win-x64` | **Medium** | 正常 |
| 同一套 Lumen 复制一份 | `D:\project\clash-halo\.tmp\...` | **Low** | — |
| `halo-host.exe`（未签名，Go） | `D:\software\halo-probe` | **Medium** | — |
| `halo-host.exe` / `clash-halo.exe` | `D:\project\clash-halo\build\windows-x64` | **Low** | 失败 |
| 同一份构建复制到 | `D:\software\clash-halo-probe` | **Medium** | 日志 `托盘图标已创建` |

也就是说：**这台机器把 `D:\project` 下的可执行文件以低完整性（Low）启动**，
同样的文件放到 `D:\software` 下就是 Medium。Windows 禁止 Low 完整性进程调用
`Shell_NotifyIcon`（返回“拒绝访问”），`systray` 因此初始化失败、托盘图标不出现。
宿主日志会写：

```
[host] 托盘图标未创建（integrity=Low desktop=WinSta0\Default taskbar=found）…
```

**修法**：把应用放在正常安装位置运行，不要放在 `D:\project`（工程/工作区）下。
实测复制到 `D:\software\clash-halo-probe` 后，`clash-halo.exe` 与 `halo-host.exe`
都是 Medium，日志出现 `托盘图标已创建`，图标正常。

如果想确认当前状态：

```powershell
pwsh -File scripts/show-process-integrity.ps1 clash-halo halo-host
```

### 4.1 是谁在按路径降权：NTFS 完整性标签

根因是**目录树上的 Low 强制性完整性标签**，不是安全软件的规则：

```
icacls "D:\project\clash-halo"
      Mandatory Label\Low Mandatory Level:(OI)(CI)(NW)      <- 显式设在本目录
icacls "...\build\windows-x64\halo-host.exe"
      Mandatory Label\Low Mandatory Level:(I)(NW)           <- 继承而来
      S-1-4-974875378-23363189:(I)(W,D,DC)                  <- 沙箱令牌的 SID
```

- `(OI)(CI)` 表示这个标签会传播给所有子项；`(NW)` 是“不可向上写”。
- 同一份可执行文件放到没有该标签的目录（`D:\software`、`%LOCALAPPDATA%`）就是
  Medium，托盘正常——这是“同一字节、只换路径”的对照结论。
- ACL 里出现的 `S-1-4-…`（非唯一权威）SID 是**受限/沙箱令牌**创建的对象的特征。
  也就是说这棵树是由**沙箱化的工具执行**写入的（本仓库的构建就是在那种环境里跑的），
  它给产物打上了 Low 标签。火绒与此无关：它只记录了一条**已允许**的
  `通过WMIC结束进程` 审计项，那是测试进程清理子进程，不是降权。

**修法**（需要管理员：改完整性标签要写 SACL，而这些对象的所有者是外部 SID，
普通用户会得到“拒绝访问”）：

```powershell
# 管理员 pwsh
pwsh -File scripts/fix-integrity-labels.ps1          # 默认处理 D:\project\clash-halo
pwsh -File scripts/fix-integrity-labels.ps1 -Path <其他目录>
```

脚本会递归把标签设为 Medium 并抽查两个 exe；若仍有个别对象失败，按提示先
`takeown` 取得所有权再重跑。处理完重新启动应用，`host.log` 应出现
`托盘图标已创建`。

**不想动权限时**：把应用放到正常安装位置运行，例如
`pwsh -File scripts/build-windows.ps1 -OutDir D:\software\clash-halo`，
已验证该路径下为 Medium、托盘正常。

### 4.2 曾经误判为原因、但已排除的项

- **签名**：给同一份 Lumen 副本用本项目的自签名证书签名后，反而从 Medium 变成 Low，
  而未签名的副本是 Medium。签名（尤其“有签名但机器不认”的状态）不是解药，
  不要把它当作这次托盘问题的修法。
- **应用清单**：给 `halo-host.exe` 嵌入 `asInvoker` 清单后，完整性级别仍为 Low。
- **语言/框架**：C# 与 Go 在同一个路径下表现一致。
- **COM 初始化、CBSize（952/976/984）**：在同一路径/同一完整性级别下都不改变结果。
- **`HKCU\...\AppHost\EnableWebContentEvaluation`**：改回原始值后行为不变。

## 5. 排查这类问题时的两个陷阱

1. **`Start-Process` 会等提示答复**：它走 `ShellExecuteEx`，提示未处理时调用不返回。
   想非阻塞启动要用 `CreateProcess`（`UseShellExecute = $false`）或 `cmd /c start`。
   反过来这也有用：`CreateProcess` 能启动而 `ShellExecute` 不能，说明拦截在 shell 层
   （SmartScreen/区域警告），而不是提权（提权对两者都生效）。
2. **不要用 `Start-Job` + `Start-Process` 判断“是否被拦”**：
   长时间的 GUI 子进程会占住 job 的输出句柄，job 一直不结束，看起来像被提示卡住，
   实际进程已经起来了。可靠的判据是「目标进程是否真的出现」。
3. **按进程名统计会串味**：同名进程可能早已在运行（例如用户自己的实例），
   按名字取最后一行会读到别人的 pid。按 pid 精确测量，测量前先结束同名进程。

## 6. 为什么同样是未签名，C# 项目（Nornia / Lumen）不弹

- **不是语言差异**，也不是清单差异。
- Lumen 放在 `D:\software` 下运行时是 Medium，所以托盘正常；把同一套程序复制到
  `D:\project` 下就变成 Low。Nornia 之前测到 Low，也是因为它在 `D:\project` 下。
- 因此**真正起作用的是路径**，见 §4；把程序放到正常安装目录即可。

## 7. 已知的、与提示无关的差异

`halo-host.exe` 与 `halo-tun-service.exe` 是 Go 直接产出的，
**没有内嵌应用清单**，
`clash-halo.exe`（Flutter runner）与 Nornia 都有 `asInvoker` 清单。
本次实测表明清单不是提示的原因（给 `halo-host.exe` 嵌入 `asInvoker` 清单后行为不变），
但补齐清单仍值得做：可声明 DPI 感知、避免 Windows 的安装程序启发式判断。
SDK 的 `mt.exe` 可以把清单直接写进已编译的 PE（必须在签名之前做，写清单会作废签名）。
